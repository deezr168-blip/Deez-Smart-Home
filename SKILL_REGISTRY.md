# Skill registry

What skills exist for this project, what each is for, where they overlap,
and what was deliberately not built. Hand-maintained.

This is **not** `AUTOMATION_REGISTRY.md`. That file is generated by
`automate/scripts/procmem.py registry` from recorded *workflows* (scripts,
skills, tools) and currently has a corrupted header (finding D1 in
`WORKFLOW_AUDIT.md`). This one indexes **skills only**, with their triggers and
boundaries, so two skills do not compete for the same request.

Last updated 2026-10-12. Evidence and scoring: `WORKFLOW_AUDIT.md`. Test
results: `SKILL_VALIDATION_REPORT.md`.

## 1. The installed skill specification, as observed

Checked against the installed validator
(`skill-creator/scripts/quick_validate.py`, from the account-synced skills) and
against all 153 `SKILL.md` files present on this machine. Claude Code
**2.1.296**.

| Rule | Source |
|---|---|
| Location: `.claude/skills/<name>/SKILL.md` in the project (versioned with the repo), or `~/.claude/skills/<name>/` for the user | existing project skills; user skills |
| Exactly one `SKILL.md` per skill; supporting files in subfolders, never a second `SKILL.md` | `quick_validate.py` |
| Required frontmatter: `name`, `description` | all 153 files |
| `name`: lowercase letters, digits and single hyphens; at most 64 characters | `quick_validate.py` |
| `description`: at most 1,024 characters; no angle brackets; carries the *when to use*, because it is the triggering mechanism | `quick_validate.py`, `skill-creator` |
| Keys the validator accepts: `name`, `description`, `license`, `allowed-tools`, `metadata`, `compatibility` | `quick_validate.py` |
| Keys also seen in the wild: `argument-hint` (51 files), `disable-model-invocation` (27), `user-invocable` (9), `version` (6), `audience` (6), `when_to_use` (2) | survey of 153 files |
| Invoke by `/<name>`, or automatically when the description matches | existing usage (`/automate`, `/improve-system`) |

The three pilots use `name`, `description` and a `metadata` block (version,
origin, status) only. They do **not** use `allowed-tools`, because that key
pre-approves tools and would change this project's permission behaviour; the
read-only guarantee is instead enforced inside the bundled scripts and tested.

### Pilot details

**`session-orient`** · version 0.1.0 · `scripts/orient.py`, `references/regimes.md`
- *Invoke:* `/session-orient`, or on "orient", "where are we", "resume a session", "which rules apply", "where do I push", or before committing. It deliberately does **not** claim "carry on", "next" or "keep going", which are `improve-system`'s triggers; see the hand-off row in section 3.
- *Inputs:* none. Everything comes from git state and the repository's own instruction files.
- *Output:* a short block: branch, regime, allowed and forbidden push targets, gate, protected paths, warnings. `--scope` adds a per-file verdict. `--json` for machines.
- *Writes:* nothing. No network. No `fetch`, `commit`, `push`, `checkout` or `config`; the script's git wrapper refuses them and the self-test proves it.
- *Stops and asks when:* the branch matches no known regime; any file falls outside the allowed paths; any file is blocked.

**`recovery-triage`** · version 0.1.0 · `scripts/triage_plan.py`, `references/symptoms.md`, `references/recovery-safeguards.md`, `references/incident-template.md`
- *Invoke:* `/recovery-triage`, or on a report that something is stale, down, locked out, missing, failing to deploy, or needs rolling back.
- *Inputs:* the symptom in the owner's words; optionally the one-word result of `casaray_sync_status.sh` and any pasted diagnostic output.
- *Output:* ordered read-only checks (marked HOST, REPO or LIVE-READ), what must not be done, and an incident record with `UNKNOWN` wherever the evidence is missing.
- *Writes:* nothing to the repository. The incident record is returned in the conversation; filing it is the owner's call.
- *Hard stops:* authentication, users and tokens; `configuration.yaml`; restoring a backup; restarts; anything that unlocks, disables a camera or lowers security; deleting anything. It may **prepare** a plan for these, marked `NOT RUN, NEEDS APPROVAL`, and nothing more.

**`provenance-register`** · version 0.1.0 · `scripts/check_register.py`, `assets/templates/`, `references/status-vocabulary.md`, `tests/fixtures/`
- *Invoke:* `/provenance-register`, or on building or checking an equipment register, inventory, evidence log, quote or purchase comparison, or a report that states owners, models, ratings, measurements, prices or dates.
- *Inputs:* the existing register if there is one (its columns are kept as they are), plus whatever sources the owner has supplied.
- *Output:* a register where every row has a `Status` and a `Source`, missing data is the literal word `UNKNOWN`, and the linter passes; plus a list of the questions that would resolve each unknown.
- *Writes:* only the file the owner names. Never uploads, shares, emails or buys without an explicit yes.
- *Does not do:* entity verification inside the Home Assistant repository (that is `improve-system`'s `references/evidence-rules.md`).

## 3. Which skill takes which request

The boundary rows are the ones most likely to be confused.

| If the request is about… | Use | Not |
|---|---|---|
| starting a session, resuming, "which branch rules apply", "where do I push", checking scope before a commit | `session-orient` | — |
| "carry on", "next", "keep going" | `improve-system` owns these triggers, but **run `session-orient` first on any branch other than `ha-deploy`**: `improve-system` is V2-only and its push steps are forbidden on V3 branches (finding D5) | — |
| a card or view that *renders* wrongly, truncates, or asserts something it cannot see | `improve-system` | `recovery-triage` |
| the wall iPad showing a stale dashboard, a deploy that will not apply, a kiosk header that will not hide, a disk filling, a rollback, lost login or configuration | `recovery-triage` | `improve-system` |
| an entity that is unavailable or missing | `improve-system` (`references/evidence-rules.md`) | `recovery-triage` |
| a register, inventory, evidence log, quote or purchase comparison, or measurements in a report | `provenance-register` | — |
| "what do I keep doing by hand", scoring repetition, building a helper | `automate` | — |
| a vendor comparison with TCO and negotiation points | `operations:vendor-review` first, then `provenance-register` to check the figures | — |

`dashboard_check.py` and the other gates are not skills and are not duplicated
by any of these.

## 6. Placement and promotion

The pilots live in the project so they are versioned with the repository and
travel with it. Two consequences:

- They exist on **`casaray-v3-design` only**. The V3 rules forbid merging any V3 branch into `ha-deploy`, so sessions on that line will not see them until the files are copied across by a route you approve.
- `provenance-register` is written to be project-neutral. To use it outside this repository, copy its directory to `~/.claude/skills/provenance-register/`. Note that the user-level folder in a cloud container is **ephemeral**: it is not versioned and does not survive the container, so the copy in Git remains the source of truth.

## 7. Maintenance rules

- One skill, one job. If a request fits two skills, fix the boundary table above rather than widening either skill.
- A skill that wraps a script keeps the mechanical part in the script and the judgement in `SKILL.md`; the script has a `--selftest`.
- Update this file in the same commit as the skill it describes, and re-run the checks in `SKILL_VALIDATION_REPORT.md`.
- Skills read repository facts at run time rather than copying them. The one exception, `session-orient`'s regime table, carries a drift check that warns when the text it was written from changes.
