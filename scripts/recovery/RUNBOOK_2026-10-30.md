## Step 0 — get the tools onto the Green over Git (no credential, nothing pasted)

The repository is public, so this is an anonymous HTTPS read. It touches only `/tmp` inside the
Terminal & SSH add-on: not `/config`, not the host clone `deez_repo`, and not the deploy token.

```sh
GIT_TERMINAL_PROMPT=0 git -c credential.helper= clone -q --depth 1 -b recovery/phase0-diagnostics \
  https://github.com/deezr168-blip/Deez-Smart-Home /tmp/casaray_src
sha256sum /tmp/casaray_src/scripts/recovery/fetch_casaray_tools.sh     # must equal the table above
sh /tmp/casaray_src/scripts/recovery/fetch_casaray_tools.sh            # prints two VERIFIED lines
rm -rf /tmp/casaray_src
```

`fetch_casaray_tools.sh` fetches the branch again, anonymously, into its own temporary bare
repository, which it removes on exit. It checks both scripts against the pinned hashes and writes
`/tmp/casaray_evidence.sh` and `/tmp/register_casaray.sh` **only if both match**. On any mismatch
it writes neither, and it never runs them. Compare the two hashes it prints with the table above.

**Undo:** `rm -f /tmp/casaray_evidence.sh /tmp/register_casaray.sh`. Nothing else exists to undo.

## Step 2 — register CasaRay (changes `configuration.yaml`, restarts Core; needs approval)

```sh
sh /tmp/register_casaray.sh check      # read-only: READY or BLOCKED: <reasons>
sh /tmp/register_casaray.sh apply      # only after approval; type APPLY when asked
```

`check` changes nothing:
- it takes no lock and writes no file;
- it never calls `ha backups new`, `ha core check` or `ha core restart`, which the test harness
  asserts;
- its only calls are `ha core info` and an unauthenticated `GET /manifest.json`.

It prints one row per gate, then any `WARN:` lines, then `READY` or `BLOCKED: <reasons>`. If
the 18/10 picture still holds, expect `READY`. These are the outcomes that would change
the plan:

| Line | Meaning | Next |
|---|---|---|
| `lovelace (outside comments) PRESENT` | `configuration.yaml` already has a `lovelace:` key | stop; merge by hand, never append a second key |
| `casaray-v2 ALREADY MENTIONED` | something already registers it | run `verify` instead |
| `.storage/lovelace_dashboards` … `USES /casaray-v2` | a UI dashboard holds the URL | stop; owner decision |
| `dashboards/casaray_v2.yaml MISSING` | the dashboard file itself is gone | stop; it must be synced first |
| `themes/deez_your_name.yaml MISSING; no verified source` | no theme, and no verified copy in `deez_repo` | stop |
| `Core liveness probe` not answering | a restart could not be verified | stop |
| `WARN: … does not load 'themes: …'` | the theme would not load | apply still works; the theme waits |

`apply` works in this order:

1. It takes a full backup and verifies it.
2. It creates a new run folder `/config/_recovery/casaray-register-<stamp>/` holding a byte-exact
   copy of `configuration.yaml` and a copy of the script.
3. It installs the theme file only if it is missing and the `deez_repo` copy matches the pinned
   hash.
4. It appends the 12-line dashboard-only block.
5. It runs `ha core check`, then restarts Core and confirms a new boot.

It puts everything back by itself on a failed check, a refused or unconfirmed restart, a Core that
does not come back, or recovery mode. **The terminal page disconnects during the restart.** The
script keeps running; reopen the Terminal panel to see the result.

Then check: Settings → Dashboards lists CasaRay as a YAML-file dashboard, and `/casaray-v2/home`
opens on the iPad.

**Rollback:**

- Use the `rollback` command that `apply` printed. It runs the copy of the script in the run
  folder, so it works even after `/tmp` is cleared. It refuses if `configuration.yaml` was edited
  since.
- By hand instead: copy `configuration.yaml.pre` from the run folder back over
  `/config/configuration.yaml`, run `ha core check`, then `ha core restart`.
- The backup taken in item 1 is the last resort.

## Step 3 — theme (pick one)

Frontend `20260930.3` ignores the dashboard-level `theme: CasaRay`. Only a view's own `theme:` is
applied, so after Step 2 CasaRay shows in each device's profile theme.

**Option A, no file change.** On the wall iPad, choose Profile → Theme → CasaRay. Undo: set the
Theme back to the default. This needs the theme file loaded, which Step 2 provides.

**Option B, per-view theme.** This is a repository change and needs the owner's permission to push
`ha-deploy`.

1. On `ha-deploy`, apply the patch:
   ```sh
   git am scripts/recovery/theme/casaray_per_view_theme.patch
   ```
   The patch file comes from this branch. Then run `bash scripts/ha_validate.sh` (it must exit 0),
   record the batch in the tracking documents as `CLAUDE.md` requires, and push `ha-deploy` and
   `claude/ha-dashboard-upgrades-wui7ig`.
2. On the Green, once the host clone has the commit, run:
   ```sh
   sh /config/deez_repo/scripts/sync_casaray_to_config.sh
   ```
   It copies only CasaRay's dashboard and theme. It keeps `.bak.<stamp>` copies of what it
   replaces, and it never touches the legacy dashboard. **No restart is needed**: Core 2026.10.1
   re-reads a YAML dashboard when its modification time changes. Refresh the browser.
3. Do this **after** Step 2. Both scripts pin the current dashboard hash `77a49916…`. With the
   themed file, `register_casaray.sh` only warns, and the evidence script reports `DIFFERS`. That
   is expected: `c8e23950…` is the themed version.

The patch is purely additive: 28 `theme: CasaRay` lines and 2 comment lines, no deletions. With
those removed, the parsed dashboard is identical to `ha-deploy`. It applies cleanly to `18a4e5d`,
and so does its reverse.

**Rollback:**
