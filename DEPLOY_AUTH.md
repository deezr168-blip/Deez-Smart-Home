# Unattended deployment — why the scheduled `git fetch` fails, and how to fix it

The manual deploy from the Studio Code Server terminal works. The identical
script run by the Home Assistant automation fails at `git fetch origin
ha-deploy`. This document is the diagnosis, the fix, and the verification
procedure.

**Scope note.** The environment that produced this branch has no `/config`
mount, no supervisor socket and no network route to the instance. Steps 1-4
below must be run on the host. Everything in `scripts/` has been syntax-checked
and executed here; nothing in this document has been run against Home
Assistant.

---

## The cause

**Studio Code Server and Home Assistant Core are separate containers.** They
share `/config` and nothing else — not `/root`, not `/home`, not each other's
package sets.

Git credentials created in the Studio Code Server terminal — `~/.gitconfig`,
`~/.git-credentials`, a cached PAT, `~/.ssh/` — live in *that container's*
filesystem. The Home Assistant process that executes `shell_command` cannot see
any of them. The repository is private, so an unauthenticated HTTPS fetch is
rejected. Hence: manual works, scheduled does not, with the same script and the
same clone.

Four things differ between the two contexts, and any of them alone breaks the
fetch:

| | Studio Code Server terminal | Home Assistant `shell_command` |
|---|---|---|
| Credentials | in that container's `$HOME` | **not present** |
| `HOME` | a real login home | inherited from the HA process; may be unset |
| `PATH` | login shell PATH | HA's process PATH, often minimal |
| tty | yes — git *can* prompt | none — git blocks, then HA kills it at 60s |

`safe.directory` is a fifth candidate: git 2.35.2+ refuses a repository owned by
a different uid ("detected dubious ownership"), which is exactly the shape of a
clone made by one container and fetched by another.

**Do not fix before confirming which.** The current log line `ERROR: git fetch
failed` is generated by the script itself and is emitted for *any* non-zero
exit — including exit 127, `git: not found`, which is a PATH problem and not an
authentication problem at all. Step 1 exists to remove that ambiguity.

---

## Step 1 — capture git's real stderr

Two edits to `/config/deploy_deez_dashboard.sh`. Nothing else in the script
changes, so the YAML validation, HA config check, atomic deployment, rollback
backup and `ha-deploy` branch protections are preserved by construction.

**1a.** As the first executable lines, after the shebang:

```sh
LOG=/config/deploy_deez_dashboard.log
exec >>"$LOG" 2>&1          # every subsequent stdout AND stderr lands in the log
. /config/deploy_env.sh     # environment + credentials (see Step 3)
```

**1b.** Wherever the script currently runs the fetch, make it verbose and print
the real error and exit code before the existing failure message:

```sh
if ! git fetch --verbose origin ha-deploy; then
    rc=$?
    echo "ERROR: git fetch failed (exit $rc)"   # keep whatever the script did here
    exit "$rc"
fi
```

> **The likeliest reason the log has no git stderr.** If the `shell_command` is
> declared with a redirect —
> `deploy: "/config/deploy_deez_dashboard.sh >> /config/deploy_deez_dashboard.log 2>&1"`
> — that redirect may never happen. Home Assistant does not run a shell for a
> command with no template placeholders; it splits on whitespace and execs, so
> `>>`, the path and `2>&1` are passed to the script as three literal
> arguments. The `exec >>"$LOG" 2>&1` in 1a fixes this properly, because the
> script then owns its own logging regardless of how it is invoked. Once it is
> in place, simplify the `shell_command` to just the script path.

## Step 2 — reproduce from the failing context, not the terminal

`scripts/deploy_diagnose.sh` prints the execution context, the tooling, the
repository ownership, the effective git config, which credential files are
visible, and then runs `git fetch --dry-run --verbose` with full stderr — all
into the same log. It is read-only, and it redacts tokens from its own output.

```sh
cp scripts/deploy_diagnose.sh /config/deploy_diagnose.sh
chmod +x /config/deploy_diagnose.sh
```

Add to `configuration.yaml` and restart:

```yaml
shell_command:
  deez_deploy_diagnose: "/bin/sh /config/deploy_diagnose.sh"
```

Run it from **Developer Tools → Actions → `shell_command.deez_deploy_diagnose`**
— this is the point of the exercise, because that is the environment that
fails. Running it in the Studio Code Server terminal answers the wrong
question. Then read section 7 of the log.

If the clone is not at one of the paths it probes, set `DEEZ_REPO`.

## Step 3 — fix, according to the verdict

### 3a. Credential (expected: "could not read Username", or 403)

Create the token file **on the host**, never in this repository:

```sh
printf 'DEEZ_GH_TOKEN=<your-fine-grained-token>\n' > /config/.deez_deploy.env
chmod 600 /config/.deez_deploy.env
cp scripts/deploy_askpass.sh /config/deploy_askpass.sh
chmod 700 /config/deploy_askpass.sh
cp scripts/deploy_env.sh    /config/deploy_env.sh
```

Use a **fine-grained** personal access token, scoped to
`deezr168-blip/Deez-Smart-Home` only, with **Contents: Read-only** — the deploy
path only ever fetches. Set an expiry and calendar the renewal.

`deploy_env.sh` exports `GIT_ASKPASS`, so the token reaches git through the
askpass protocol. It never enters the remote URL, `.git/config`, the reflog,
the process argument list, or any tracked file. `scripts/deploy_askpass.sh`
holds no secret — it echoes an environment variable.

Confirm the remote is HTTPS. If it is an SSH URL, either switch it —
`git -C <repo> remote set-url origin https://github.com/deezr168-blip/Deez-Smart-Home.git`
— or use a deploy key instead (3c).

### 3b. Environment (`git: not found`, dubious ownership, unset HOME)

Already handled by `deploy_env.sh`, which pins `PATH`, guarantees `HOME`,
points `GIT_CONFIG_GLOBAL` at `/config/.deez_gitconfig` so both containers read
the same config, sets `safe.directory`, and sets `GIT_TERMINAL_PROMPT=0` so git
fails loudly in one second instead of hanging until Home Assistant's 60-second
timeout kills it.

### 3c. SSH deploy key — more secure, if available

A read-only deploy key is tighter than a PAT: repo-scoped by construction, and
no expiry to renew. **Check first** that the Home Assistant container ships an
ssh client — section 2 of the diagnostic reports this — because a minimal
container often does not, and git over SSH cannot work without it.

```sh
mkdir -p /config/.ssh && chmod 700 /config/.ssh
ssh-keygen -t ed25519 -N '' -f /config/.ssh/deez_deploy_ed25519
ssh-keyscan github.com > /config/.ssh/known_hosts
chmod 600 /config/.ssh/deez_deploy_ed25519
```

Add the `.pub` to the repository's **Settings → Deploy keys**, write access
**off**, then point the remote at `git@github.com:...`. `deploy_env.sh` picks
the key up automatically via `GIT_SSH_COMMAND`.

## Step 4 — verify from the automation, not by hand

A manual run proves nothing here; it is the context that already worked.

1. Push a commit to `ha-deploy`.
2. **Do not** run anything in the terminal. Wait for the 15-minute automation,
   or fire it from Developer Tools → Actions → the deploy `shell_command`,
   which executes in the same environment as the schedule.
3. `tail -n 120 /config/deploy_deez_dashboard.log`.

It is working when the log shows, in one automated run: a fetch that prints
`From https://github.com/...` and the new ref, the YAML validation passing, the
HA config check passing, the atomic swap, the rollback backup being written,
and the new commit hash — with no manual git command in between. Then remove
the `deez_deploy_diagnose` shell_command.

Confirm the deployed commit matches `git rev-parse origin/ha-deploy`.

## Security notes

- `/config` is readable by any add-on granted config access — Studio Code
  Server, Terminal & SSH, Samba. Mode 600 protects `/config/.deez_deploy.env`
  from non-root processes, but not from another add-on running as root. That is
  the reason for insisting the credential be **read-only and scoped to this one
  repository**: it bounds the blast radius to "someone can read a private repo
  they could already read from this machine".
- Never enable `GIT_CURL_VERBOSE` or `GIT_TRACE` permanently. They print the
  `Authorization` header into the log. If you need them to chase a TLS problem,
  enable them for a single run and truncate the log afterwards.
- `/config/deploy_deez_dashboard.log` will contain repository paths and commit
  hashes. Redact before pasting it anywhere public; the diagnostic already
  redacts token-shaped strings from its own output.
