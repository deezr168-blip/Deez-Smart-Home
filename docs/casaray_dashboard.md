# CasaRay-native dashboard: design notes

## What "native to CasaRay" means here

[CasaRay](https://casaray.dev/) is an Apple-native Home Assistant client
(iPhone, iPad, Mac, widgets, Shortcuts, Apple Watch). It keeps Home Assistant as
the source of truth and then maps entities into a normalised model:

> summary first → control groups → active rooms → individual devices,
> with cameras and energy as first-class sections

The Home Assistant side of this house had 431 entities across 10 areas — the
kind of setup CasaRay is explicitly built to tame ("turns a large Home Assistant
setup into a home you can read in seconds: what is open, what is on, what needs
attention"). The dashboard in `home-assistant/dashboards/casaray_home.yaml`
restructures Home Assistant's own UI along that same model, so moving between
CasaRay on a phone and Home Assistant on a browser doesn't mean re-learning
where things live.

## The mapping

| CasaRay concept | How this dashboard implements it |
|---|---|
| Summary first | Home view badges: weather, lights on, doors open, media playing, needs attention, offline. Each badge hides itself at zero, so the row is empty when the home is idle. |
| Control groups | "Everything" section — lights off, media off, fans off, close covers. Domain-wide, not curated lists. |
| Active rooms | Area cards for the 8 real rooms, each showing its own alerts (motion, occupancy, doors, problems), its climate readings (temperature, humidity, illuminance), and inline light/switch/fan/cover controls. |
| Individual devices | One drill-down subview per room, generated by Home Assistant's `area` view strategy. Tapping a room card navigates there. Subviews stay out of the tab bar. |
| Cameras | Dedicated view, grouped by area. |
| Energy | Dedicated view built on Home Assistant's native energy cards, tied to the existing Energy dashboard config. |
| Infrastructure | The `Network` pseudo-area (96 entities: eero, AdGuard, Tapo camera plumbing, TP-Link hub) is pushed into a separate **System** view, out of the room flow. |

### Rooms

Real rooms, in the order the dashboard presents them:

Living Room · Dining · Kitchen · Parents Room · Ray Bedroom · Guest Room ·
Garage · Backyard

`Network` and `Energy` are pseudo-areas — organisational buckets, not places.
They are deliberately excluded from the rooms flow: `Network` becomes the System
view, `Energy` is represented by the Energy view rather than as a room.

### Alert and sensor classes

The area cards surface the device classes that actually exist in this home:

- **Alerts** — `motion`, `occupancy`, `door`, `problem` (all present live);
  `window`, `smoke`, `gas`, `moisture` are included too, so they light up
  automatically if such a device is ever added.
- **Sensors** — `temperature`, `humidity`, `illuminance`.
- **Controls** — `light`, `switch`, `fan`, `cover`.

`connectivity` is deliberately *not* an alert class: 16 entities in this home
carry it (mostly "Cloud connection" sensors on Tapo devices), and surfacing them
per-room would make every room look permanently alarmed. They're covered instead
by the single `CasaRay Offline` summary sensor.

## The safety property

This repo's rule (`docs/entity_inventory.md`) is that entity IDs are never
invented or guessed. That rule shaped the whole design rather than constraining
it after the fact — and the result is a dashboard that's more robust than a
hand-written one, not less:

- **Area cards / area view strategies** address rooms by area ID and populate
  themselves from whatever is in the room.
- **Group buttons** target `entity_id: all` within a domain.
- **Summary sensors** iterate live state objects rather than naming entities.

So no card in the dashboard can reference a nonexistent entity, and nothing goes
stale when a device is renamed, replaced, or added. The genuinely
entity-specific cards — cameras, people, weather — are quarantined in
`home-assistant/dashboards/generated/` and written from the live registry by
`scripts/ha_verify.py --write`.

### The one remaining assumption

The dashboard does depend on **area IDs**. Those are recorded as the slugified
area names (`Living Room` → `living_room`), which is Home Assistant's default
but not guaranteed — an area renamed after creation keeps its original ID.

`scripts/ha_verify.py` closes that gap: it lists every real area, flags any ID
the dashboard uses that doesn't exist, suggests the closest match, and exits
non-zero. Run it once before installing. A card pointing at a missing area
renders empty rather than erroring, which is exactly the kind of silent failure
worth catching up front.

## Known limitations

- **Area cards show one camera per area.** Four Tapo cameras share the `Network`
  area, so the shipped stub can only surface one of them. `--write` fixes this
  by emitting a card per camera.
- **The Energy view depends on the Energy dashboard being configured** in
  Settings → Dashboards → Energy. The cards render empty otherwise.
- **`Ray Bedroom`'s roller shade was `unavailable`** at the time of writing, and
  the Parents Room AC was the only `climate` entity in the house. The cover and
  climate controls are wired up regardless — they'll populate when those devices
  report.
- **Requires HA 2025.2+.** On older versions the sections views and area
  strategies won't render.
